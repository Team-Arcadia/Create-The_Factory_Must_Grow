▸ Scope of this test pass ▸ Périmètre de cette passe

Neymor16's b291e878 retest still showed +40 spool durability burned regardless of target percentage (5% target burns 90 instead of 50, 15% burns 190 instead of 150, 100% burns 1040 instead of 1000). Constant offset, not a multiplier — meaning the previous server-only sidedness fix was correct but did not address the actual leak.

Root cause was the layered structure of performRecipe: three potentially-overlapping branches (resistor / coil / generic), with stacked if (spool.has(...)) guards meant to prevent overlap. About 40 ticks worth of drain leaked through the generic branch's amountWinded++ ; spool.set(SPOOL_AMOUNT, ...) path on resistor / coil items — the dedicated branch returned but the next tick's control could still slip into the generic branch under certain field states.

The 1705c9e5 fix replaces all three branches with strictly mutually-exclusive paths:

  • resistor + constantan_spool — its own closed transaction (read RESISTANCE, gate on target, drain spool, write component, return)
  • coil + copper_spool — symmetric to the resistor path
  • generic recipe — runs ONLY when slot item is neither resistor nor coil; if (isResistor || isCoil) return; short-circuits these items before the generic branch can be considered

Tests below verify the +40 leak is gone for both kinds of target item, that the generic recipe path still works for non-resistor/coil winding recipes, and that nothing in the rewrite broke spool conversion / persistence / slot interaction.
