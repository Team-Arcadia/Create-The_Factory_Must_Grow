▸ Scope of this test pass ▸ Périmètre de cette passe

Four follow-up fixes shipped in 242a522b after Neymor16's f94fbeef report (one server crash + four behaviour regressions). Tests are grouped per fix: a primary test that validates the fix and 1–2 collateral tests that catch the most likely regression each fix could have caused.

  • VAT-NPE — server crashed within seconds of inserting an asphalt_mixture into a vat (NPE at VatBlockEntity.handleRecipe:604 on this.recipe.getRollableResults()). Cause: tank.drain in tickRecipe triggered a fluid-update listener that called getMatchingRecipe; with the water just drained the recipe no longer matched and this.recipe was set to null mid-cycle. The fluid-output and item-output loops then NPE'd. Fix captures the recipe in a local activeRecipe before the drain so the rest of the transaction stays consistent.
  • WIND-OVERDRAW — winding a resistor at 5% target consumed ~90 spool durability instead of 50, and at 100% target produced 960 ohm instead of 1000. performRecipe had a resistor branch that returned after one decrement, but once RESISTANCE reached its target the branch skipped and execution fell into the generic recipe branch below — which kept decrementing the spool every tick (incrementing amountWinded but not RESISTANCE). Fix adds an early return when the slot item is a resistor / coil already at its target.
  • BFO-PUMP-STUTTER — Create's mechanical pump extracted 128 mB then immediately stalled after the previous fix added level.invalidateCapabilities on every onFluidChanged. Each invalidation made the pump drop its cached handler and re-fetch on the next tick, killing the steady-state stream. Fix removes the per-tick invalidation; only the read() invalidation remains (the actual chunk-reload bug we wanted to fix).
  • BFO-FUEL-OVERFLOW — once the fuel buffer hit its 64-item cap, additional coal_coke_dust dropped on the BFO fell through into the input slot and blocked the recipe (only break-and-replace recovered). collectItems tested 'is fuel AND fuel < cap' and on cap-reached fall-through it stuffed the item into inputInventory. Fix: any item tagged BLAST_FURNACE_FUEL always continues — when the cap is full the item simply isn't picked up. Same guard applied to FLUX for symmetry.
